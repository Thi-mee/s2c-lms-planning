# Entity: Notification

> **Status:** Confirmed domain baseline; linked feature gates remain\
> **Authority:** Canonical — entity representation\
> **Owner module:** Notifications\
> **Updated:** 2026-09-17

## Purpose

Durable transactional-email intent generated by a business or identity action, not an in-app notification center.

## Key fields

| Field | Conceptual type / requirement | Meaning |
|---|---|---|
| id | identifier, required | Stable record identity |
| organization_id | reference, required | Owning Organization |
| recipient_user_id | reference, required | Same-org recipient |
| event_type | enum, required | invite, cohort_start, forum_reply, course_completion; identity recovery messages as needed |
| payload | bounded structured data | Template inputs; minimize sensitive values |
| channel | enum, required | email for MVP |
| status | enum, required | pending, processing, sent, failed |
| deduplication_key | identifier, required | Unique business intent within organization |
| attempts / next_attempt_at / lease_until | counter/timestamps | Durable retry/claim state |
| created_at / sent_at | timestamps, required / conditional | Creation and delivery acceptance |
| last_error_code | optional bounded text | Non-secret operational failure classification |

## Organization and integrity

All referenced records must belong to the same organization. Apply the [model conventions](README.md#shared-constraints) and the additional course/cohort/run constraints below. Field types describe the conceptual contract; concrete SQL types and indexes are implementation work.

## Authorization and audit

Use the single [role/grant policy](../01-domain/roles-and-permissions.md); this document does not create a competing CRUD permission matrix. Mutations are owner-module operations, never arbitrary cross-module entity updates. Required sensitive-action audit commits in the same transaction ([ADR-13](../06-architecture/decisions.md#adr-13--atomic-state-and-durable-effects)).

## Lifecycle, relationships and constraints

Persist intent atomically with the triggering state. Worker claims a lease and sends outside the transaction; retries survive process failure. Unique organization/deduplication_key prevents duplicate intent creation. SMTP uncertainty can cause a duplicate delivery: do not claim exactly-once email. Mark sent on provider acceptance, not assumed receipt.

Invitation/reset tokens must never be exposed in diagnostics or retained indefinitely in readable payloads; use protected short-lived delivery material and cleanup. Recheck revoked/expired invite intent before sending stale queued links. Old cohort jobs must validate current schedule; failed sends are inspectable/retryable with bounded backoff. Final rendering/access to referenced data remains organization-scoped. A failed external send never undoes committed enrollment/completion; inability to persist required intent fails the original transaction.

## Open questions

Additional notification categories/subscriptions are not MVP scope. Retention follows [Q57](../00-product/open-questions.md#q57). Retry/backoff thresholds are engineering choices.
